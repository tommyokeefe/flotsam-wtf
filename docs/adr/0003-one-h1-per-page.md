# Exactly one H1 per page; the site title is not a heading

Every page rendered the site name as `<h1><a href="/">FLOTSAM</a></h1>` in `Layout.astro`'s header. On `/what` and post pages that produced two competing `<h1>`s, so no single element unambiguously named the page and the document outline claimed the site name and the page title were peers. On `/` and `/who` it produced the opposite defect: the only `<h1>` was the site name, so neither page had a heading of its own at all. The rule now is that **every page carries exactly one `<h1>`, and it names that page rather than the site.** The masthead is therefore a `<p class="site-title">` restyled to render identically, which is why it looks like a heading but is not one, and why turning it back into an `<h1>` would reintroduce the bug.

Where a page's visual design does not want a heading on screen, the `<h1>` is hidden with `.visually-hidden` rather than omitted. The post index is the only current case: a list of dated links under the masthead needs no on-screen label, so its `<h1>Posts</h1>` exists purely for the outline and assistive tech. This is deliberately the exception and not the default — `/who` gained a visible `# Who` rather than a hidden one, because a prose Page reads better with a heading and `/what` already set that precedent. Reach for the hidden variant only when adding a visible heading would genuinely damage the page.

Two consequences worth stating. Because the site title no longer matches sakura's `h1` selector, `Layout.astro`'s scoped block restates `font-size`, `font-weight` and `line-height` by hand; if sakura's heading styles are ever changed, the masthead will not follow and must be updated alongside. And `/what` is the one page whose heading does not match its own `title` frontmatter or its nav label (`# FLOTSAM (noun)` versus "What"), which is a deliberate bit of voice left untouched here rather than an oversight.
