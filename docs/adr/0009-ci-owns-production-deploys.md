# CI owns production deploys, so Vercel's automatic deploys are off for main

Vercel's Git integration normally deploys production on every push to `main`. For this site it is switched off, for `main` only, in `vercel.json` (`git.deploymentEnabled`). Production is instead deployed by the `Publish and deploy` workflow (`.github/workflows/publish-and-deploy.yml`), which builds the site, audits the manifest, publishes Documents to the ATmosphere (ADR 0008), and only then calls a Vercel deploy hook.

**This is the setting most likely to be switched back on.** A merge that doesn't deploy on its own looks like a misconfigured integration, and turning the default back on looks like the fix. It isn't: the workflow already deploys, so re-enabling it gives two production deploys per merge, and the first one races the publish it is meant to follow.

**Why the order matters.** A Post's HTML names its Document in its head (#42), and it learns that Document's AT-URI by asking the PDS at build time, because the rkey is assigned when the record is written and nothing about it is stored in the repo (ADR 0008). A new Post's Document doesn't exist until publishing creates it. If Vercel built on push, it would usually build before the publish had run, and the Post's first production deploy would lack its reference until some later, unrelated deploy happened to rebuild it. Deploying after publishing makes the first deploy the right one.

**Publishing can never block a deploy.** The deploy job runs whether or not the publish job succeeded; only a cancelled run skips it. A PDS that is down, a refused plan, or an expired app password leaves the site shipping without a Document reference on new Posts, and the workflow fails visibly so someone notices. The ATmosphere is somewhere Posts are announced, never something the site depends on to be up (#35).

**Previews are untouched.** `deploymentEnabled` only names `main`, and Vercel keeps deploying every branch it doesn't name. So preview deployments, and reading a Draft on one (ADR 0004), work as they did. The workflow also only runs on `main`, so a preview never publishes anything, and a Draft visible in a preview never gets a Document.

**Only the tip of `main` publishes, and the hook deploys whatever `main` is now.** A run whose commit is no longer the tip of `main` skips publishing, because re-running an old run would otherwise publish a stale manifest over newer Documents: a fresh checkout gives every file a new mtime, so the publish script's own freshness check can't catch it. The deploy hook takes no commit, so if a second merge lands while a run is publishing, that run deploys a build whose newest Post isn't published yet. The second run publishes and deploys again shortly after, so the gap closes by itself.

**What this costs.** Production now depends on GitHub Actions running and on the `VERCEL_DEPLOY_HOOK_URL` secret being set. If either is missing, a merge does not reach production and the workflow says so. The way out is to redeploy from the Vercel dashboard, or re-run the latest run of the workflow (an older one deploys but won't publish). A deploy started by hand is harmless: it builds whatever is on `main` and looks up whatever Documents exist.

**One gap, accepted for now.** The deploy runs even when `audit:manifest` fails, which is the case where a Draft has leaked into a production build. Vercel's production build would include that Draft too. This is no worse than before this change, when nothing audited a deploy at all, but the audit could also stop the deploy in future if a leaked Draft should count as worse than a stalled site.

Revisiting this means either accepting that a new Post's first deploy lacks its Document reference, or finding another way to put publishing ahead of Vercel's own build, such as a deployment check that holds the production alias until publishing finishes.
