# Use Astro Content Collections for posts

Posts were individual pages under `src/pages/posts/*.md(x)`, each with its own `layout:` frontmatter and no shared schema — every feature (post index, tags, search, thumbnails) would have had to independently glob and parse raw frontmatter. We moved posts to `src/content/posts/<slug>/index.md(x)` (colocated images, own folder per post) with one Zod schema and a single render route, so that `tags`, `image`, and `draft` each land in one typed, validated place as they arrive rather than being re-implemented per feature. The trade-off: adding a post is no longer "drop a file and it's automatically a route" — it's data rendered through a shared route — and the per-post `layout:` override is gone (it wasn't being used for anything but consistency). Existing URLs (`/posts/wind`, `/posts/circle-of-concern`) are preserved by keeping slugs flat and equal to folder names.

Three details of the implementation are deliberate and would otherwise look like mistakes. The route is `[slug].astro`, **not** the rest-param `[...slug].astro` that Astro's docs use: slugs are flat here, and a single-segment param makes that structural instead of merely documented. The loader pattern is `**/index.{md,mdx}`, so only a file named `index` is a Post — a scratch file left in a post's folder is silently ignored rather than silently published at a URL nobody intended, which is the better of the two silent failures. And the route renders `<h1>{title}</h1>` from frontmatter, so **post bodies must not open with their own H1**; both original posts repeated their title verbatim in the body, and that duplication was removed so a title is written once. A side effect is that the title no longer carries the markdown pipeline's auto-generated slug anchor (`id="wind"`), which nothing links to.
